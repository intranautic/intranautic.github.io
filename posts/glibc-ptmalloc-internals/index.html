Glibc PTMalloc Internals

Dec 8, 2022

The GNU C Library is complex, and its default memory allocator, PTMalloc, is no exception. Within this post, I’ll document the allocator’s internals and how they have evolved across versions of Glibc.

These notes grew out of years of being bombarded with heapnote challenges. I’m writing them partly for my own sake: keeping track of the differences between versions has become difficult without a reference.

We’ll start with the heap and chunk layout, then work through the bins, arenas, and allocation and deallocation algorithms. The algorithm walkthroughs focus on Glibc 2.31; keep the version in mind when comparing them with other releases.

This post focuses on understanding the allocator. I’ll cover exploitation techniques separately. If I’ve stated anything incorrectly, please feel free to let me know through one of my contacts below.

Overview

Let’s first begin with a general definition of what the heap is and why it exists.

The heap, not to be confused with the heap data structure is a means of efficiently allocating dynamic memory to a process. This means that during runtime, a process can request a chunk of designated memory to be allocated and returned. When the process no longer needs this chunk of memory, it can be freed, which deallocates the chunk and allows for it’s reuse.

There are a couple means of allocating memory, one such technique is to rely on the process stack to allocate local variables. This can be used, and is typically more efficient as opposed to relying on a dynamic allocator; but the downside is the fact that the allocation cannot outlive the function call. Variable length arrays and alloca can use a size determined at runtime, but the local memory which resides on the call stack is deallocated when its lifetime ends. We can pass a pointer to this memory to another function, but that pointer cannot be used after the memory’s lifetime has ended.

Another form of memory allocation is that of mmap, which directly maps entire pages of memory for the process to use. The downside to this is the fact that we cannot efficiently allocate chunks of memory less than a page in size, which would be very inefficient in both time and space.

This is where the concept of dynamic memory management comes in, and how we can use memory allocators as an efficient means of allocating smaller dynamic and global chunks of memory efficiently.

Heap

So how does the heap actually work within Glibc? We would think that the process may initially utilize the mmap system call to map a large region of memory which will be designated for our program heap, but for the main arena that’s not usually the case.

The main arena normally obtains memory via MORECORE, which by default relies on sbrk. On Linux, sbrk is a library function which uses brk to change the program break, which serves to define the end of the process’s data segment. By increasing the program break, we essentially allocate memory, while decreasing the break will deallocate memory at that end of the heap.

On Linux, the kernel can also randomize the initial program break as part of ASLR. This allows for randomization of the heap’s base address.

Reading through the source of Glibc provides the statement that “By default, rely on sbrk”. Something to keep in mind however is the fact that non-main arenas use mmap-backed heaps, and even the main arena can fall back to mmap if MORECORE fails.

Malloc can also utilize mmap to directly map an individual allocation. The initial mmap threshold is 128 kilobytes, but this threshold can change, and an allocation above it may still be satisfied by a cached chunk or the existing top chunk first. A chunk carved from an mmap-backed arena heap is different from an individually mmapped chunk; only the latter has the IS_MMAPPED flag set.

The relevant paths are within sysmalloc and new_heap.

Chunk

We can refer to the term chunk as a unit of memory per allocation which is returned by the allocator. For example, when we call malloc, we are returned the address of the chunk designated for us by the allocator.

Chunks within the PTMalloc allocator utilize metadata within their headers as a means of storing important information. The following is the definition of the malloc_chunk structure within Glibc.

Something important to note is the fact that chunk sizes are multiples of MALLOC_ALIGNMENT. In Glibc 2.31, both x86-64 and i386 use an alignment of 16 bytes. The request2size macro adds SIZE_SZ bytes of overhead, rounds up for alignment, and ensures that the result is at least MINSIZE. This means that the internal chunk size and the size you request from the allocator are different quantities.

Unless stated otherwise, the sizes below refer to internal chunk sizes. The 32 bit examples refer specifically to i386, as other 32 bit architectures can have different alignment requirements.

The exact definitions can be found within request2size, the generic alignment header and the i386 alignment header.

struct malloc_chunk {
  INTERNAL_SIZE_T mchunk_prev_size;  /* Size of previous chunk (if free).  */
  INTERNAL_SIZE_T mchunk_size;       /* Size in bytes, including overhead. */

  struct malloc_chunk* fd;         /* double links -- used only if free. */
  struct malloc_chunk* bk;

  /* Only used for large blocks: pointer to next larger size.  */
  struct malloc_chunk* fd_nextsize; /* double links -- used only if free. */
  struct malloc_chunk* bk_nextsize;
};

When we allocate a chunk of memory from our allocator, it will only return to us the pointer to the usable region of the chunk. The header of the structure shown above our usable region should not be accessed or modified by the user, but this doesn’t necessarily mean that we can’t.

Looking at the structure of malloc_chunk above, the usable region of memory begins at the fd pointer. The fields fd, bk, fd_nextsize and bk_nextsize are used for free list links when applicable; while the chunk is allocated, this region holds user data. We will take a deeper look into these caching bins later on within this post.

The mchunk_prev_size field is different, as it holds the previous chunk’s size when the previous chunk is free, even if the current chunk is allocated. For an individually mmapped chunk, it instead holds the offset from the mapping’s base. The mchunk_size field holds the size of the current chunk, as well as various flags.

Before we elaborate on these flags, let’s first take a look at an ascii diagram to gain a better understanding of the chunk layout within memory.

chunk-> +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
	|             Size of previous chunk, if unallocated (P clear)   |
	+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-
	|             Size of chunk, in bytes                      |A|M|P|
mem-> +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
	|             User data starts here...                            .
	.                                                                 .
	.             (malloc_usable_size() bytes)                        .
        +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+--+

We can see that the three bits within the diagram named A, M and P reside within the mchunk_size field of the header. These flags are stored on the three lower order bits of the mchunk_size field.

Our first flag P (PREV_INUSE) is used for indicating whether or not the previous adjacent chunk is treated as allocated. When a chunk is freed through the ordinary coalescing path, malloc checks that chunk’s own PREV_INUSE flag to determine whether it should coalesce backward. To determine whether the next chunk is free, it checks the PREV_INUSE flag in the chunk after that next chunk. A chunk’s own in-use status is stored in the PREV_INUSE flag of its following chunk.

The next flag M (IS_MMAPPED) is fairly simple, as it serves to indicate that the chunk is an individually mmapped allocation. This allows the allocator to keep track of the chunk’s method of allocation, and its subsequent deallocation. This flag is not set just because an arena’s heap was obtained with mmap.

Then our last flag A (NON_MAIN_ARENA). This flag serves to indicate whether or not the chunk belongs to the main heap or not. By default PTMalloc will utilize a single global heap state for our allocator named the arena. However, when we are within a multithreaded environment the allocator must effectively manage not only the state of the main heap, but that of the other threads as well. I will elaborate on the arena further on as well.

Top Chunk / Wilderness

The top chunk (also referred to as the wilderness), is the chunk which borders the end of available memory on heap. We can also think of this chunk as a region of free memory which has not yet been allocated.

This chunk is given special treatment, as it will never be inserted into any cache bins and is only used as a last resort when other caching mechanisms cannot provide an adequate chunk.

If more memory is required on the heap, the main arena will normally try to extend it via MORECORE. Non-main arenas can grow their current mmap-backed heap or obtain a new heap. We can think of the top chunk as the free space at the end of the arena’s current heap, rather than all the free memory in the arena. After the heap has been set up, the metadata on this top chunk will contain the size of the chunk, as well as the PREV_INUSE flag which is always set. The initial dummy top is an exception, as its size is zero before the first heap is obtained.

Last Remainder Chunk

Under certain conditions, when the user requests a chunk in which the cache bins cannot satisfy, a larger free chunk which has been cached can be split and returned to the user.

When a larger regular-bin chunk is split to satisfy a small request, the allocator records the remainder in the arena’s last_remainder field and places it within the unsorted bin. This is known as the last remainder chunk. Not every split updates this field; splitting the top chunk, for example, updates the top pointer instead. I will elaborate on this process at a later point in time when explaining the cache bins.

Cache Bins

Let’s now take a closer look into the previously mentioned caching bins.

These bins serve as a means of optimizing allocation speeds and reducing fragmentation on the heap by allowing the quick retrieval of chunks which were previously in use. There are in total 5 different kinds of bins which all serve separate purposes, which we will discuss.

But why would we want to store recently freed chunks within these bins? These bins serve as a means of improving performance and reducing heap fragmentation. By caching the pointers to these freed chunks of memory, the allocator has the ability to quickly check the bins for cached chunks of the same size.

There are various kinds of bins within the current implementation of PTMalloc. Let’s take a look at their use cases, as well as various properties which make them unique.

Tcache

First, we have the tcache (Thread Local Cache), which was introduced within Glibc 2.26. In terms of functionality, the tcache is very similar to the fastbin in the sense that it serves as a set of singly linked LIFO lists which are stored in size specific bins. Unlike the fastbin, the tcache has a specific limit on the quantity of chunks within each bin as it only allows (by default) 7 free chunks per bin.

However, as the name implies, the tcache serves as a thread specific caching mechanism, meaning that there is a tcache per thread.

The following are relevant definitions for the tcache.

typedef struct tcache_entry
{
  struct tcache_entry *next;
  /* This field exists to detect double frees. */
  struct tcache_perthread_struct *key;
} tcache_entry;

typedef struct tcache_perthread_struct {
  // since glibc 2.30 counts type is uint16_t, used to be char
  uint16_t counts[TCACHE_MAX_BINS];
  tcache_entry *entries[TCACHE_MAX_BINS];
} tcache_perthread_struct;

static __thread tcache_perthread_struct *tcache = NULL;

The purpose of this bin is to provide a faster means of accessing cached chunks within multithreaded environments, as there is no longer a need to lock the arena state when accessing these thread local caches. Something important to note is the fact that the tcache takes priority over all the other bins, it will be the first bin to be accessed in the event of an allocation, and the first candidate to cache a chunk if it is of size for the tcache.

We can see the structure named tcache_perthread_struct, which serves as the thread local state which stores important information on each threads tcache. Each thread will have a tcache_perthread_struct, hence the name.

There are 64 tcache bins by default with each bin holding up to 7 entries. Both limits can be reduced through tunables, and the entry count can also be increased. Each of the tcache bins store a fixed size chunk determined by the index of the bin. On x86-64, the chunk sizes range from 32 to 1040 bytes, with a maximum request size of 1032 bytes. On i386, the chunk sizes range from 16 to 1024 bytes, with a maximum request size of 1020 bytes. An architecture with 4 byte SIZE_SZ and 8 byte alignment instead has chunk sizes from 16 to 520 bytes, with a maximum request of 516 bytes.

Fastbin

The fastbin is a set of singly linked LIFO lists which are stored within size specific bins. On x86-64, there are 10 slots in the fastbin array, but the slots reserved within the array are not the same as the range currently eligible for fastbin caching. By default, eligible chunk sizes range from 32 to 128 bytes on x86-64 and 16 to 64 bytes on i386. The maximum supported M_MXFAST setting raises these upper chunk sizes to 160 and 80 bytes respectively. The array length itself is calculated by NFASTBINS, so it can also differ with alignment and architecture.

As each entry within the fastbin are all the same size, there is no need to access from the middle of the list, so each entry only utilizes its fd pointer (which points to the next entry within the fastbin). An fd pointer of NULL indicates the end of the singly linked list.

Chunks held within the fastbin are treated as allocated chunks from the point of view of the allocator. The PREV_INUSE flag in the chunk following each fastbin chunk remains set, which prevents consolidation of that fastbin chunk. This is done at the cost of additional fragmentation, but the result is that of minimal logic which causes free to be faster.

As a result of this desire for performance, when freeing and caching chunks into the fast bin, the allocator will only check for a double free against the head of that bin, as opposed to traversing the entire singly linked list for duplicates. This has various security implications which allow attackers to abuse this bin to gain arbitrary write primitives.

To explicitly consolidate the fastbin, we must use a specialized version of free called malloc_consolidate, which releases all free chunks within the fastbin and coalesces them with other adjacent freed chunks.

The function malloc_consolidate is called from several paths. During an ordinary free, if the size after coalescing is at least FASTBIN_CONSOLIDATION_THRESHOLD and the arena’s have_fastchunks field is set, the allocator will consolidate fastbins. This macro is defined as the following.

#define FASTBIN_CONSOLIDATION_THRESHOLD  (65536UL)

Something important to note is that this is a free-time threshold, not an allocation request threshold. During malloc, a request in the large bin range will also cause consolidation if have_fastchunks is set. If an allocation reaches the top chunk and there isn’t enough space, the allocator can consolidate fastbins and retry before requesting more memory. malloc_trim and mallopt also call malloc_consolidate.

The relevant calls are within _int_malloc, the top chunk path, _int_free, mtrim and mallopt.

Small Bin

There are 62 small bins, where each are cyclic, doubly linked list with sizes ranging from 16 to 992 on i386 and 32 to 1008 on x86-64. The size of chunk each bin contains depends on the index of the bin, like the fastbin and tcache. The smallbin follows a FIFO order of operation, which means that entry insertions occur at the head of the doubly linked list, and removals take place at the tail. Each small bin only contains entries of the same size.

The small bin belongs to a bin known as the normal bin. The normal bin is split into two kinds of bins, the small and large bin.

As we might have noticed, the size of freed chunks that the small bin contains also overlaps with that of the fastbin and tcache. Eligible chunks can go directly into the tcache or fastbin when freed, but chunks enter the small and large bins through the unsorted bin. A small chunk can reach the unsorted bin when the tcache is full and it is too large for the fastbin, or when fastbins are consolidated.

Large Bin

The large bin (like the small bin), is also referred to as a normal bin.

There are 63 large bins which each maintain a doubly linked list sorted by size. Unlike the small bin, the large bin has the ability to contain chunks of different sizes. The sizes within each bin must be within a specific range however. Allocation uses best fit, with equal-size handling also attempting to avoid removing the entry which maintains the nextsize links, so this is not simply a FIFO queue.

The large bins are approximately logarithmically spaced. The source describes six groups with spacings of 64, 512, 4096, 32768 and 262144 bytes, followed by a bin for what’s left. However, the exact boundaries and quantity within each group depend on the largebin_index macros, rather than a fixed 32/16/8/4/2/1 division. On x86-64, the 63 large bins use indices 64 through 126; index 127 is unused.

The large bin range begins at 1024 bytes on x86-64 and 1008 bytes on i386. There is no fixed upper limit of 128 kilobytes. That is the initial mmap threshold, but existing arena memory can satisfy larger requests, and the threshold can change.

The previously discussed fd_nextsize and bk_nextsize pointers within the chunk are utilized within the large bin. They link one representative for each distinct chunk size within that bin, allowing malloc to skip equal-size chunks while searching. A representative can point to itself when there is only one distinct size within the bin.

The exact indexing and list operations can be found within the bin definitions and the large bin paths.

Unsorted Bin

The unsorted bin is also a circular, doubly linked list which holds free chunks of any size. There is only one unsorted bin and acts as a sort of queue for the small and large bins. The only free chunks which make it into the normal bins are those that come from the unsorted bin. The unsorted bin is also referred to as a normal bin as it is held within the same buffer as the large and small bins within the heap state.

When a chunk cannot be cached within the tcache or fastbin, the ordinary free path will consolidate it with adjacent free chunks where possible. The result is placed within the unsorted bin, unless it merges into the top chunk instead. It can remain there across allocation requests which are satisfied by earlier paths, such as the tcache. Once malloc reaches the unsorted bin, this functionality gives the allocator one chance to use a chunk before it is sorted into the small and large bins.

If the chunk is an exact fit, malloc can return it, or place it within the tcache and continue searching before returning a cached chunk. If it is not an exact fit, it will normally be moved into the small or large bin depending on its size, even if it is larger than the request. The small bin cutoff is MIN_LARGE_SIZE, which is 1024 bytes on x86-64 and 1008 bytes on i386.

There is one special case where malloc will split a chunk directly from the unsorted bin. The request must be within the small bin range, the chunk must be the only entry in the unsorted bin and equal to av->last_remainder, and its size must be strictly greater than the normalized request plus MINSIZE. The remainder is placed back within the unsorted bin and recorded as the new last remainder. Other non-exact chunks can still be selected and split later through the regular bin search, after they have been sorted.

The relevant conditions are within the unsorted bin traversal.

Let’s take a look at the following code as an example to help better visualize the process which the unsorted bin undergoes.

#include <stdlib.h>

int main(int argc, char** argv) {
  void* chunk = malloc(1040); // allocate our chunk large than fastbin & tcache size
  void* _ = malloc(24); // prevent consolidation with top chunk
  free(chunk); // place within unsorted bin
  return 0;
}

Arena

The arena generally acts as a state for the allocator and heap. This is the structure which contains the bins, as well as other important fields such as a mutex which serializes access on multithreaded processes.

Let’s now take a look at the definition of the arena within Glibc.

struct malloc_state {
  /* Serialize access.  */
  __libc_lock_define (, mutex);

  /* Flags (formerly in max_fast).  */
  int flags;

  /* Set if the fastbin chunks contain recently inserted free blocks. */
  /* Note this is a bool but not all targets support atomics on booleans. */
  int have_fastchunks;

  /* Fastbins */
  mfastbinptr fastbinsY[NFASTBINS];

  /* Base of the topmost chunk -- not otherwise kept in a bin */
  mchunkptr top;

  /* The remainder from the most recent split of a small request */
  mchunkptr last_remainder;

  /* Normal bins packed as described above */
  mchunkptr bins[NBINS * 2 - 2];

  /* Bitmap of bins */
  unsigned int binmap[BINMAPSIZE];

  /* Linked list */
  struct malloc_state *next;

  /* Linked list for free arenas.  Access to this field is serialized
     by free_list_lock in arena.c.  */
  struct malloc_state *next_free;

  /* Number of threads attached to this arena.  0 if the arena is on
     the free list.  Access to this field is serialized by
     free_list_lock in arena.c.  */
  INTERNAL_SIZE_T attached_threads;

  /* Memory allocated from the system in this arena.  */
  INTERNAL_SIZE_T system_mem;
  INTERNAL_SIZE_T max_system_mem;
};

I will now give a brief overview of each field within the structure, I recommend viewing the source of Glibc to gain a much more whole understanding of the concept.

The first field within the structure is the mutex which we know serializes access to the structure. The next field flags is a signed 32 bit integer which holds additional information about the state of the arena, the flags are as follows.

/*
   NONCONTIGUOUS_BIT indicates that MORECORE does not return contiguous
   regions.  Otherwise, contiguity is exploited in merging together,
   when possible, results from consecutive MORECORE calls.
   The initial value comes from MORECORE_CONTIGUOUS, but is
   changed dynamically if mmap is ever used as an sbrk substitute.
 */

#define NONCONTIGUOUS_BIT (2U)

#define contiguous(M) (((M)->flags & NONCONTIGUOUS_BIT) == 0)
#define noncontiguous(M) (((M)->flags & NONCONTIGUOUS_BIT) != 0)
#define set_noncontiguous(M) ((M)->flags |= NONCONTIGUOUS_BIT)
#define set_contiguous(M) ((M)->flags &= ~NONCONTIGUOUS_BIT)

The next field within the arena is have_fastchunks, which indicates that there are probably chunks within the fastbins. This is a separate integer field in Glibc 2.31, accessed through relaxed atomic operations, rather than a bit within flags. It is only a hint used to avoid unnecessary calls to malloc_consolidate.

Next is a buffer of pointers to the fastbins of the arena. The top field will contain a pointer to the top chunk of the heap and last_remainder will also point to the last remainder chunk.

The field bins is interesting, as it contains the unsorted, small and large bins within a single field. We can see that the comment above refers to each of these bins as the normal bins.

Subsequently, the field binmap is another optimization which simply holds information on the state of each bin as to prevent manually searching through the large and small bins to find free chunks.

Directly after this, we have the next and next_free fields within the arena, which contain pointers to other arenas. As we know, we can have multiple arenas within a single process. The next field forms a cyclic singly linked list which includes the main arena and all non-main arenas. The next_free field forms a non circular list of free arenas, which are arenas with no threads attached. Arenas can be shared among threads, and a non-main arena can also have multiple heaps.

The definition and initialization can be found within malloc_state and the arena code.

The next fields are well documented within the source, attached_threads will hold the number of threads attached to the arena; and the system_mem and max_system_mem will contain the memory allocated and the largest amount of memory from the system within the arena.

Heap Info

The heap_info structure serves as a means of coordinating the mmap-backed heaps which belong to a non-main arena. This structure primarily holds important information of the heap, as well as acting as a singly linked list which points to the previous heap_info structure within that arena. The main arena’s ordinary brk-backed heap does not have this header.

What follows is the definition of the structure within Glibc.

typedef struct _heap_info {
  mstate ar_ptr; /* Arena for this heap. */
  struct _heap_info *prev; /* Previous heap. */
  size_t size;   /* Current size in bytes. */
  size_t mprotect_size; /* Size in bytes that has been mprotected
                           PROT_READ|PROT_WRITE.  */
  /* Make sure the following data is properly aligned, particularly
     that sizeof (heap_info) + 2 * SIZE_SZ is a multiple of
     MALLOC_ALIGNMENT. */
  char pad[-6 * SIZE_SZ & MALLOC_ALIGN_MASK];
} heap_info;

Unlink Operation

As previously stated, the freed chunks which are cached into bins are held as linked lists. However, when retrieving such freed chunks and returning them from the allocator, we also need a mechanism to remove such chunks from their free list. This process is handled by unlink_chunk for regular doubly linked bins (previously a macro). Fastbins and tcache use separate removal paths, and some regular-bin paths update the links directly.

The function is defined as follows.

/* Take a chunk off a bin list.  */
static void
unlink_chunk (mstate av, mchunkptr p)
{
  if (chunksize (p) != prev_size (next_chunk (p)))
    malloc_printerr ("corrupted size vs. prev_size");

  mchunkptr fd = p->fd;
  mchunkptr bk = p->bk;

  if (__builtin_expect (fd->bk != p || bk->fd != p, 0))
    malloc_printerr ("corrupted double-linked list");

  fd->bk = bk;
  bk->fd = fd;
  if (!in_smallbin_range (chunksize_nomask (p)) && p->fd_nextsize != NULL)
    {
      if (p->fd_nextsize->bk_nextsize != p
	  || p->bk_nextsize->fd_nextsize != p)
	malloc_printerr ("corrupted double-linked list (not small)");

      if (fd->fd_nextsize == NULL)
	{
	  if (p->fd_nextsize == p)
	    fd->fd_nextsize = fd->bk_nextsize = fd;
	  else
	    {
	      fd->fd_nextsize = p->fd_nextsize;
	      fd->bk_nextsize = p->bk_nextsize;
	      p->fd_nextsize->bk_nextsize = fd;
	      p->bk_nextsize->fd_nextsize = fd;
	    }
	}
      else
	  {
	    p->fd_nextsize->bk_nextsize = p->bk_nextsize;
	    p->bk_nextsize->fd_nextsize = p->fd_nextsize;
	  }
  }
}

Malloc Algorithm

PTMalloc has to balance allocation speed, memory usage and fragmentation across a wide range of applications. This makes its design complex and, in my opinion, inelegant. Reusing freed chunks and consolidating adjacent free chunks are central to that balance.

The following walkthrough covers Glibc 2.31. It is a general outline; the source code is the best reference for the exact control flow in a particular version.

As we have previously stated, the allocator will attempt to use all the previously cached chunks within each of the bins as a means of optimizing allocation speeds and reducing fragmentation on the heap. What follows is the high-level abstracted order in which malloc will search for chunks within the bins. Keep in mind that there is a more convoluted algorithm which lies underneath this, which we will cover.

Tcache -> Fastbin -> Exact Small Bin -> Unsorted Bin -> Regular Bin Search -> Top Chunk -> Sysmalloc

This is only a high-level order; the paths below depend on the request size, and consolidation can cause the regular-bin search to be retried.

Let’s now dive into a high level description of the steps which malloc takes to allocate a chunk of memory. There are two functions which are responsible for the allocation of memory when we call malloc, these are __libc_malloc and _int_malloc.

__libc_malloc

https://elixir.bootlin.com/glibc/glibc-2.31/source/malloc/malloc.c#L3021

  1. Check if a malloc hook has been defined. If so, call it with the requested size and the caller’s return address. Initially, this hook is malloc_hook_ini, which clears the hook, initializes the allocator and calls __libc_malloc again.
  2. If the tcache has been enabled at compile time, check and normalize the requested size, returning null with ENOMEM if it is too large. Convert the normalized size into the appropriate tcache bin index and initialize the thread’s tcache if needed. If there is a free chunk within the corresponding enabled tcache bin, return it. Keep in mind that the tcache was introduced in Glibc 2.26, meaning that prior versions of PTMalloc won’t have this portion of code.
  3. Then, if SINGLE_THREAD_P indicates that the process is single threaded, return the result of _int_malloc on the main arena without taking the arena mutex. On Linux this is a runtime check, not an option to compile without thread support.
  4. Otherwise, call arena_get, which obtains an arena and locks it if one is available, then make a call to _int_malloc with the arena.
  5. If the result of _int_malloc is null and the arena pointer is not null, then attempt to find another arena to retry allocation.
  6. Finally, if the arena pointer is not null then unlock the mutex which synchronizes the arena, and return the allocation result.

_int_malloc

https://elixir.bootlin.com/glibc/glibc-2.31/source/malloc/malloc.c#L3511

  1. Check if the requested size is within viable range to be allocated and convert it into an internal representation (adding SIZE_SZ / alignment / padding).
  2. Next, check the arena pointer which was passed as an argument, if the arena is null then it will fall back to sysmalloc to allocate a chunk from mmap.
  3. If the normalized size is within the range of the fastbin, then check the corresponding fastbin for a free chunk. After selecting a chunk to return, it can also perform a procedure known as tcache stashing. This term simply refers to moving additional chunks of that same size from the corresponding fastbin into the tcache, while the fastbin is not empty and the enabled tcache bin is not full.
  4. Then if the normalized request is within the small bin range, check the corresponding small bin for cached chunks. This means less than 1024 bytes on x86-64 or 1008 bytes on i386. After selecting a chunk to return, the small bin path can also perform a tcache stash from that same size bin.
  5. Else, the request is within the large bin range. Calculate its large bin index, and if have_fastchunks is set, call malloc_consolidate. This consolidates the fastbins with adjacent free chunks and places the results within the unsorted bin, or merges them into the top chunk. This also reduces fragmentation on the heap which is caused by the fastbins lack of consolidation.
  6. Next, check and sort the entries within the unsorted bin. Please refer to the unsorted bin section of this post as reference of its internal operations.
  7. For a large request, search the corresponding large bin for the smallest chunk which fits. If no chunk is returned, use the binmap to search larger regular bins. This later search also applies to small requests, so a larger small bin chunk can be split to satisfy a smaller request. A remainder of at least MINSIZE is placed within the unsorted bin; otherwise the whole chunk is used.
  8. Finally, if no chunks can be found within the bins, try splitting the top chunk, leaving at least MINSIZE behind. If the top chunk is too small and have_fastchunks is set, consolidate the fastbins and retry the search. Otherwise, call sysmalloc to obtain more memory. This can directly mmap the allocation, extend the main arena through MORECORE, or grow or create a non-main heap.

Keep in mind, it is not necessary to know the entire step-by-step process in which malloc takes to allocate chunks for us, just a general understanding of the allocator should do just fine. However I would still recommend that you read through the source just to familiarize yourself with it.

Free Algorithm

We’ve seen how malloc retrieves chunks from the bins. Let’s now look at how free places them there, following the deallocation path through __libc_free and _int_free.

__libc_free

https://elixir.bootlin.com/glibc/glibc-2.31/source/malloc/malloc.c#L3085

  1. Check for a free hook, if present it will call the hook with a few debugging parameters.
  2. Then check if the pointer to our chunk is null, if so then it will simply return and do nothing. Calling free with a null pointer will have no effect.
  3. Next, check if the chunk has it’s IS_MMAPPED bit set, if so then simply deallocate the chunk with munmap and return. Before unmapping, it can also raise the dynamic mmap threshold and set the trim threshold to twice that value.
  4. Else, if tcache has not yet been initialized, then initialize the tcache. Find the arena in which the chunk belongs to and pass the chunk and the arena to the internal _int_free mechanism, which will handle the primary caching and deallocation mechanism. After this, return.

_int_free

https://elixir.bootlin.com/glibc/glibc-2.31/source/malloc/malloc.c#L4153

  1. First, we perform a few security checks on the chunk we want to free. Check for address wraparound and a misaligned pointer, then check that the chunk size is at least MINSIZE and a multiple of MALLOC_ALIGNMENT. These checks reject some invalid pointers and sizes, but do not prove that the pointer is a valid allocation.
  2. If tcache is enabled and initialized, and the chunk falls within an enabled tcache bin, inspect the key field within its user region. If the key equals this thread’s tcache pointer, traverse that bin to check whether the chunk is already present. If a duplicate is found, abort the process. The traversal confirms the key match, as ordinary payload data could coincidentally contain the same value.
  3. If the chunk qualifies for the tcache and the corresponding bin is not full, insert the free chunk into the tcache and return without coalescing.
  4. Else, if the chunk size falls within the bounds of the fastbin, perform the fastbin checks and insert it into the corresponding fastbin.
  5. If none of the previous conditions are met and the chunk is not individually mmapped, take the arena lock if needed and check the neighboring metadata. Coalesce backward and forward with adjacent ordinary free chunks where possible. If the result borders the top chunk, merge it into top; otherwise place it within the unsorted bin. The chunks within the unsorted bin are not placed into the small and large bins until they have been given one chance in malloc.
  6. If the resulting size reaches FASTBIN_CONSOLIDATION_THRESHOLD, consolidate fastbins if have_fastchunks is set, then consider trimming the main arena or the current non-main heap.
  7. Else, for an individually mmapped chunk reaching the mmap branch of _int_free, deallocate the region via munmap. Normal calls through __libc_free handle these chunks before calling _int_free.

The relevant paths are within __libc_free and _int_free.
